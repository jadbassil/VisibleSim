# <<appName>> — VisibleSim RL training environment

Generated by `utilities/rlAppGenerator`. This app turns a VisibleSim simulation
(robot family: **<<moduleName>>**) into a gym-style environment: the coordinator
module opens a TCP socket on port **<<gymPort>>** and exchanges observations and
actions with an external Python trainer.

```
applicationsSrc/<<appNameLc>>/
  <<appNameLc>>.cpp              main()
  <<appNameLc>>BlockCode.hpp/.cpp  the environment logic (fill in the TODO hooks)
  gymServer.hpp/.cpp            generic TCP bridge (no edits needed)
  Makefile
  USAGE.md                      this file
  train/                        NumPy trainer (env, model, train, export)
applicationsBin/<<appNameLc>>/config.xml   starter world
```

## 1. Build

Add the app to the build once, then compile:

```sh
# one-time: add <<appNameLc>> to the SUBDIRS line of applicationsSrc/Makefile
#           (rlgen.py --register does this for you)
make -C applicationsSrc <<appNameLc>>
# or build everything from the repo root:
make -j$(sysctl -n hw.ncpu)
```

## 2. Run the environment

The binary blocks waiting for a trainer to connect; it does not self-terminate
(the Python side owns the episode lifecycle and kills the process on `close()`).

```sh
cd applicationsBin/<<appNameLc>>
./<<appNameLc>> -c config.xml -t       # headless
./<<appNameLc>> -c config.xml -R -x    # graphical, fastest
```

## 3. Train

```sh
cd applicationsSrc/<<appNameLc>>/train
python3 -m pip install -r requirements.txt
python3 env.py        # smoke test: connects, runs a few "stay" steps
python3 train.py --episodes 10
```

`train.py` launches the binary for you (see `DEFAULT_BINARY` in `env.py`), so you
do **not** need to start the simulator separately.

## 4. Protocol

Newline-delimited JSON over TCP (`127.0.0.1:<<gymPort>>`).

* **C++ → Python** (sent on connect and after every step):

  ```json
  {"type":"obs","step":N,"max_steps":200,"reward":0.0,"done":false,
   "grid_size":[x,y,z],
   "blocks":[{"id":1,"pos":[x,y,z],"neighbors":[2,-1,...],"moves":[[x,y,z],...]}]}
  ```

* **Python → C++**:

  ```json
  {"type":"step","actions":{"1":0,"2":1}}
  ```

  Action `0` = stay; `k>=1` = move to the `(k-1)`-th cell of that block's
  `moves` list.

## 5. What you must implement

The socket/observation plumbing is complete; the task-specific parts are TODO
hooks in `<<appNameLc>>BlockCode.cpp`:

| Hook | Purpose |
|------|---------|
| `getAvailableMoves(b)` | enumerate legal destination cells (uses your family's motion rules, e.g. `<<moduleNameLc>>MotionEngine` / `getAllMotions()`). Until filled in, blocks have only the "stay" action. |
| `applyAction(b, action)` | turn a chosen action into a real motion event. |
| `computeReward()` | scalar reward for the step (your objective). |
| `isEpisodeDone()` | episode termination (defaults to `step >= MAX_STEPS`). |

Tune the per-block features in `VisibleSimEnv.obs_to_arrays` (`train/env.py`) to
match what your policy needs.

## 6. Export weights

`train.py` periodically calls `write_weights(...)`, producing `weights.bin` in the
`VSW1` format. You can also round-trip-test the serializer standalone:

```sh
cd applicationsSrc/<<appNameLc>>/train
python3 export_weights.py     # writes weights.bin, reloads it, verifies CRC
```

### Weight file layout (`VSW1`)

The format is the stable contract between Python and any (future) C++ consumer.
All integers are little-endian `uint32`; all data is little-endian `float32`,
row-major:

| Field | Bytes | Notes |
|-------|-------|-------|
| magic | 4 | `"VSW1"` |
| version | 4 | `1` |
| n_tensors | 4 | number of named tensors |
| per tensor | … | `name_len(u32)` · `name(bytes)` · `ndim(u32)` · `dims(ndim·u32)` · `prod(dims)·f32` |
| crc32 | 4 | `zlib.crc32` (IEEE 802.3) over every preceding byte |

## 7. Using PyTorch or another framework

The C++/socket side is framework-agnostic — only `train/` is NumPy. To switch to
PyTorch (or JAX / TF / Stable-Baselines3 / Gymnasium):

1. **Policy** — replace `model.py` with an `nn.Module`. The gym API
   (`reset()` / `step()`) in `env.py` already matches Gymnasium/SB3, so you can
   wrap `VisibleSimEnv` directly.
2. **Observations** — keep `env.py` as-is, or adapt `obs_to_arrays()` to emit
   tensors / a `torch_geometric` graph (the JSON observation carries per-block
   positions, neighbor ids and legal moves — enough to build a graph).
3. **Export** — rewrite `export_weights.py` to walk your framework's
   `state_dict()` / parameters and call `write_weights({name: tensor.numpy()})`,
   keeping the **same `VSW1` layout** above so the file stays loadable.
4. Add the dependency to `requirements.txt`.

```python
# PyTorch export sketch
import torch
from export_weights import write_weights
sd = {k: v.detach().cpu().numpy() for k, v in policy.state_dict().items()}
write_weights(sd, "weights.bin")
```

## 8. Loading & using weights at deployment

This skeleton is **training-only**: it streams to Python at runtime and does not
yet load weights inside the simulator. When you want on-robot inference (no
Python in the loop), add a deploy path that consumes `weights.bin`. The format
above is all you need; the steps:

1. **Read the file in C++.** A reference loader mirroring `load_weights()`:

   ```cpp
   // policyWeights.cpp — load a VSW1 file into name -> flat float vector + dims
   #include <fstream>
   #include <map>
   #include <vector>
   #include <cstdint>
   #include <stdexcept>
   #include <zlib.h>   // crc32; link with -lz  (or vendor a small CRC32)

   struct Tensor { std::vector<uint32_t> dims; std::vector<float> data; };

   std::map<std::string, Tensor> loadWeights(const std::string& path) {
       std::ifstream f(path, std::ios::binary);
       std::vector<char> blob((std::istreambuf_iterator<char>(f)), {});
       if (blob.size() < 12 || std::string(blob.data(), 4) != "VSW1")
           throw std::runtime_error("bad magic");
       uint32_t stored;
       std::memcpy(&stored, blob.data() + blob.size() - 4, 4);
       if (crc32(0, (const Bytef*)blob.data(), blob.size() - 4) != stored)
           throw std::runtime_error("CRC mismatch");

       size_t off = 4;
       auto u32 = [&]{ uint32_t v; std::memcpy(&v, blob.data()+off, 4); off+=4; return v; };
       if (u32() != 1) throw std::runtime_error("bad version");
       uint32_t n = u32();
       std::map<std::string, Tensor> out;
       for (uint32_t i = 0; i < n; ++i) {
           uint32_t len = u32();
           std::string name(blob.data()+off, len); off += len;
           uint32_t ndim = u32();
           Tensor t; uint32_t count = 1;
           for (uint32_t d = 0; d < ndim; ++d) { uint32_t s = u32(); t.dims.push_back(s); count *= s; }
           t.data.resize(count);
           std::memcpy(t.data.data(), blob.data()+off, count*sizeof(float)); off += count*sizeof(float);
           out[name] = std::move(t);
       }
       return out;
   }
   ```

2. **Where to wire it.** In `<<appNameLc>>BlockCode::startup()`, read a weight
   path from the config (`<deploy weights="..."/>` via `parseUserElements`) or a
   `VS_DEPLOY_WEIGHTS` environment variable, load it **once**, and have each
   module run the same forward pass as `model.py` (matmul + ReLU + masked argmax
   over its legal moves) to pick an action locally — no socket, no Python.

3. **Validate.** `python3 export_weights.py` re-reads the file and checks the CRC,
   so a load failure points to the writer, not the reader.

> Tip: if you would rather not depend on zlib, copy a 20-line CRC32 (IEEE 802.3)
> implementation into `policyWeights.cpp`; it must match Python's `zlib.crc32`.
